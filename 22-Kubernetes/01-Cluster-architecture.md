# Kubernetes: архитектура кластера

> **Уровень:** начальный · **Время:** 35–45 минут · **Предварительные знания:** Linux, Docker, YAML и основы сетей.

## Модель

Kubernetes управляет желаемым состоянием приложений через API. Control plane принимает и обрабатывает изменения; worker nodes запускают Pod и поддерживающие их компоненты. Контроллеры постоянно сравнивают фактическое состояние с желаемым и пытаются устранить расхождения.

~~~text
kubectl / API client
        │
        ▼
API server ──► хранилище состояния
        │
        ▼
Controllers / Scheduler
        │
        ▼
Worker node: kubelet + container runtime + Pods
~~~

Схема упрощена: реальный кластер включает дополнительные компоненты и зависит от дистрибутива.

## Основные роли

- **API server:** основной интерфейс управления объектами.
- **Scheduler:** выбирает узел для Pod, который ещё не назначен.
- **Controllers:** согласуют фактическое состояние с желаемым.
- **kubelet:** обеспечивает выполнение назначенных Pod на узле.
- **Container runtime:** запускает контейнеры.
- **etcd:** в типичной архитектуре хранит состояние control plane.

## Декларативная модель

Пользователь описывает желаемое состояние, например число реплик Deployment. Kubernetes не запускает команду один раз и не забывает о ней: контроллер продолжает сверять состояние и реагировать на отклонения.

## Практика чтения состояния

В подключённом учебном кластере:

~~~bash
kubectl get nodes
kubectl get pods -A
kubectl get events -A --sort-by=.lastTimestamp
~~~

Если команды не работают, сначала проверь контекст и доступ к кластеру. Не выполняй команды изменения, пока не убедился, что подключён к нужной среде.
