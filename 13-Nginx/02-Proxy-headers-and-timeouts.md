## 1. Proxy меняет контекст запроса

Приложение за Nginx обычно видит сетевым peer сам Nginx, а не исходного клиента. Если приложению нужен адрес клиента, схема проксирования должна передавать его явно. Базовый фрагмент внутри подходящего `location`:

```nginx
location / {
    proxy_pass http://app_backend;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_connect_timeout 3s;
    proxy_send_timeout 30s;
    proxy_read_timeout 30s;
}
```

Это иллюстрация директив, а не готовый полный конфиг: `app_backend` должен быть определён в `upstream` или быть корректным адресом.

- `Host` помогает приложению выбрать виртуальный хост и сформировать ссылки.
- `X-Real-IP` передаёт адрес, который Nginx видит как клиента.
- `X-Forwarded-For` хранит цепочку адресов проксирования.
- `X-Forwarded-Proto` сообщает схему внешнего запроса.

## 2. Доверять заголовкам можно не от любого клиента

Заголовки `X-Forwarded-For` и подобные легко подделать, если приложение принимает их напрямую из интернета. Доверенная схема должна определить, какие прокси разрешено считать источниками этих заголовков. Приложение не должно считать произвольное значение заголовка подтверждённым клиентским IP.

Если перед Nginx есть load balancer, то `$remote_addr` может быть адресом балансировщика. Настройка real-IP-модуля должна ограничивать доверенные источники конкретными адресами/сетями инфраструктуры, а не доверять всем подряд.

## 3. Различайте три таймаута

- `proxy_connect_timeout`: сколько ждать установления соединения с upstream.
- `proxy_send_timeout`: интервал без успешной передачи данных в upstream.
- `proxy_read_timeout`: интервал между чтениями данных от upstream, а не универсальный лимит общей длительности запроса.

Увеличение всех таймаутов не устраняет медленное приложение. Оно может только дольше удерживать соединения и ресурсы. Сначала установите, где задержка: соединение, передача запроса, обработка приложения или чтение ответа.

## 4. Практическая диагностика

Проверяйте конфигурацию до reload:

```bash
sudo nginx -t
sudo nginx -T
```

Команда `nginx -T` может выводить конфигурационные значения и пути; перед публикацией вывода проверьте его на наличие внутренних адресов и чувствительных данных. После проверки смотрите error log и логи приложения с одним и тем же временем запроса.

Сравните два независимых теста:
1. запрос к приложению напрямую из разрешённой диагностической сети;
2. тот же запрос через Nginx.

Если напрямую быстро, а через прокси медленно, исследуйте сетевой путь, заголовки, TLS-терминацию и настройки proxy. Если оба пути медленные — проблема, вероятно, глубже в приложении или его зависимостях.

## 5. Частые ошибки

- Перезаписывать `X-Forwarded-For` одним значением и терять цепочку.
- Доверять forwarded-заголовкам от внешнего клиента.
- Считать `proxy_read_timeout` общей длительностью HTTP-запроса.
- Увеличивать таймауты без измерения задержки и числа активных соединений.
- Применять конфиг без `nginx -t` и плана возврата.
