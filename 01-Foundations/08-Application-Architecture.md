# Архитектура приложения: клиент, сервер и зависимости

> **Уровень:** начальный · **Время:** 30–40 минут · **Предварительные знания:** основы ОС, сеть и файлы.

## Типовая схема

~~~text
Пользователь / клиент
        │ HTTP(S)
        ▼
Reverse proxy / web server
        │
        ▼
Backend / API
        │
        ├──► База данных
        ├──► Кеш
        └──► Внешние API
~~~

Это распространённая модель, но не единственная. Компоненты могут располагаться на одной машине или в разных средах.

## Конфигурация и секреты

Конфигурация задаёт параметры поведения: адрес базы, порт, режим и лимиты. Секреты — пароли, токены и приватные ключи — требуют отдельной защиты. Не записывай реальные секреты в исходный код или Git.

~~~bash
if printenv DATABASE_URL >/dev/null 2>&1; then
  echo "DATABASE_URL задана"
else
  echo "DATABASE_URL отсутствует"
fi
~~~

Команда проверяет наличие переменной окружения, не выводя её значение. Это важно, потому что значение может содержать пароль или токен.

## Логи, метрики и traces

- **Логи** фиксируют события и детали.
- **Метрики** показывают числовое поведение во времени.
- **Трассировки** связывают обработку запроса между компонентами.

Ни один сигнал не заменяет остальные. Метрика может показать рост задержки, лог — ошибку, trace — компонент, на котором запрос замедлился.

## Разбор недоступного приложения

Если клиент не получает ответ:
1. проверь DNS и сетевую доступность;
2. проверь, слушает ли proxy нужный порт;
3. проверь состояние backend;
4. проверь зависимость от базы или внешнего API;
5. сопоставь время запроса с логами и метриками.

Не начинай с перезапуска всех компонентов: это может уничтожить диагностические доказательства и увеличить влияние сбоя.
