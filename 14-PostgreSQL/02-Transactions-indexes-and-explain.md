# PostgreSQL: транзакции, индексы и EXPLAIN

## Результат обучения

Вы научитесь видеть транзакцию как единицу согласованного изменения, понимать назначение индексов и читать базовый план запроса без поспешного добавления индексов «на всякий случай».

## Предварительные знания

- [База данных, схема и первый SQL-запрос](./01-Database-schema-and-queries.md)
- Базовые SELECT, WHERE и ORDER BY.

## 1. Транзакция — единая операция

```sql
BEGIN;
UPDATE accounts SET balance = balance - 25 WHERE id = 1;
UPDATE accounts SET balance = balance + 25 WHERE id = 2;
COMMIT;
```

Два обновления относятся к одной логической операции перевода. Если между ними обнаружена ошибка, приложение должно выполнить `ROLLBACK`, чтобы не оставить только одну сторону операции. Этот пример учебный: реальная платёжная логика также требует проверок существования счетов, достаточности средств, конкурентных изменений и обработки повторов.

Не держите транзакции открытыми дольше необходимого: они могут удерживать блокировки и мешать очистке старых версий строк.

## 2. Что даёт индекс

Индекс помогает находить строки без полного просмотра таблицы в подходящих запросах. Например:

```sql
CREATE INDEX idx_events_created_at ON events (created_at);
SELECT id, created_at
FROM events
WHERE created_at >= now() - interval '1 day'
ORDER BY created_at;
```

Индекс не бесплатен: он занимает место и добавляет работу при INSERT/UPDATE/DELETE. Планировщик может выбрать последовательное чтение, если таблица мала или запрос возвращает большую долю строк. Не создавайте индекс только потому, что поле встречается в WHERE.

Порядок колонок в составном индексе важен. Индекс `(tenant_id, created_at)` хорошо соответствует фильтрации по tenant и диапазону времени, но не эквивалентен индексу только по `created_at`.

## 3. Читайте план, а не угадывайте

```sql
EXPLAIN
SELECT id, created_at
FROM events
WHERE created_at >= now() - interval '1 day'
ORDER BY created_at;
```

`EXPLAIN` показывает предполагаемый план. `EXPLAIN ANALYZE` действительно выполняет запрос и показывает фактические времена и число строк; используйте его осознанно, особенно для тяжёлых запросов или запросов с побочными эффектами. Для безопасного исследования начинайте с SELECT и ограниченной тестовой базы.

Сравнивайте:
- estimated rows и actual rows;
- тип доступа (Seq Scan, Index Scan, Bitmap Scan);
- стоимость сортировки;
- расхождение оценок и факта;
- время на узлах и объём прочитанных строк.

Большой Seq Scan сам по себе не ошибка. Он может быть оптимальным при чтении значительной части таблицы.

## 4. Лаборатория

В локальной тестовой БД создайте небольшую таблицу событий и заполните её тестовыми строками. Сравните `EXPLAIN` запроса с фильтром по времени до и после индекса. Не ожидайте обязательного изменения плана на крошечной таблице: планировщик учитывает стоимость, а не просто наличие индекса.

Проверьте транзакцию с двумя обновлениями и намеренно выполните `ROLLBACK`. Убедитесь, что данные вернулись к исходным значениям. Работайте только с учебными данными, не запускайте экспериментальные UPDATE на production.

## 5. Типовые проблемы

- Транзакция открыта в приложении и забыта после ошибки.
- Индексы замедляют запись и занимают неожиданно много диска.
- Планировщик оценивает число строк неверно из-за статистики или распределения данных.
- `EXPLAIN ANALYZE` выполняет запрос, а не просто анализирует его.
- Наличие индекса ошибочно принимают за гарантию быстрого запроса.
