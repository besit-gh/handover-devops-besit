# PostgreSQL: резервное копирование и проверка восстановления

## Результат
Понимать разницу между наличием backup-файла и доказанной возможностью восстановить сервис в требуемое время.

## Зависимости
[База, схема и SQL](./01-Database-schema-and-queries.md), [Транзакции, индексы и EXPLAIN](./02-Transactions-indexes-and-explain.md), основы хранения и прав Linux.

## 1. Backup — это проверяемая процедура
Резервная копия полезна, если:
- известен её охват и момент времени;
- данные защищены от несанкционированного доступа;
- хранение и срок удержания соответствуют требованиям;
- известны зависимости восстановления;
- restore регулярно проверяется в изолированной среде.

**RPO** описывает допустимую потерю данных по времени. **RTO** — целевое время восстановления сервиса. Это требования, которые нужно проверять упражнениями, а не просто числа в документации.

## 2. Логический backup
Для учебной базы можно использовать `pg_dump`:

```bash
pg_dump --format=custom --file=demo.dump demo_db
pg_restore --list demo.dump
```

Команды запускайте под подходящей учётной записью и в контролируемой среде. Файл дампа может содержать всю базу: защищайте его как исходные данные и не добавляйте в Git или публичные артефакты.

Для восстановления custom-format dump обычно используют `pg_restore` в заранее созданную целевую базу. Перед восстановлением уточните, нужно ли сохранить существующие данные, роли, владельцев и расширения. Не экспериментируйте с `--clean` на базе, где есть нужные данные.

## 3. Проверка восстановления
В изолированной тестовой БД:
1. создайте несколько тестовых строк;
2. выполните backup;
3. измените или удалите тестовые строки;
4. восстановите дамп в отдельную чистую базу;
5. проверьте количество строк и контрольные значения;
6. измерьте длительность и запишите ограничения.

Успешное завершение команды restore не гарантирует логическую корректность восстановленного приложения. Нужны проверки схемы, данных и ключевого пользовательского сценария.

## 4. Где logical dump недостаточен
Для больших баз и требований к point-in-time recovery может потребоваться физический backup и архивирование WAL. Это отдельная архитектура с требованиями к согласованности, хранению, мониторингу и процедурам восстановления. Выбор зависит от размера данных, RPO/RTO, доступной инфраструктуры и возможностей команды.

## Типичные ошибки
- Хранить единственную копию рядом с исходной базой.
- Не защищать дамп от чтения и утечки.
- Считать exit code backup единственным критерием успеха.
- Не проверять роли, расширения, версии и владельцев.
- Ни разу не измерять время восстановления.
