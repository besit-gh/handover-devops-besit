# Пирамида тестирования и обратная связь

> **Уровень:** начальный · **Время:** 30–40 минут · **Предварительные знания:** Git и понимание приложения.

## Зачем нужны разные виды тестов

Разные тесты ловят разные классы ошибок и имеют разную стоимость поддержки.

- **Unit:** быстро проверяет небольшую единицу логики в изоляции.
- **Integration:** проверяет взаимодействие нескольких компонентов.
- **End-to-end:** проверяет пользовательский путь через большую часть системы.

Это не жёсткий закон и не требование всегда иметь определённую пропорцию. Важно выбрать самый дешёвый тест, который надёжно обнаруживает нужный класс дефекта.

## Пример

Для HTTP API:
- unit-тест проверяет преобразование входных данных;
- integration-тест проверяет запрос к тестовой базе;
- end-to-end-тест проверяет полный сценарий через HTTP.

Если тест зависит от нестабильной внешней системы, результат может быть случайным. Изолируй зависимости, используй тестовые данные и делай ошибки воспроизводимыми.

## Что должно быть у полезного теста

- понятное условие и ожидаемый результат;
- независимость от случайного порядка выполнения;
- контролируемые тестовые данные;
- полезное сообщение при падении;
- повторяемость на локальной машине и в CI.

## Практика

Возьми небольшую функцию или скрипт. Определи один нормальный случай, граничный случай и ошибочный ввод. Для каждого запиши ожидаемое поведение до запуска теста.

## Контрольные вопросы

1. Когда unit-тест полезнее end-to-end?
2. Почему integration-тест может быть медленнее и менее изолированным?
3. Что такое flaky test?
4. Почему успешный pipeline не гарантирует отсутствие всех дефектов?

## Итог

Тесты создают обратную связь о конкретных свойствах системы; их ценность зависит от того, какой риск они действительно проверяют.
