# Проверки качества перед выпуском

## Цель
Связать Git, тесты, сборку контейнера и выпуск так, чтобы ошибка останавливалась до публикации, а релиз имел проверяемый артефакт и план возврата.

## Последовательность
1. Validate — формат и статические проверки.
2. Test — unit- и интеграционные тесты.
3. Build — образ из конкретного commit.
4. Verify — smoke test и health endpoint.
5. Publish — публикация версии образа.
6. Deploy — выпуск после нужного approval.
7. Observe — post-deploy проверка.

Сборка должна происходить из того же commit, который прошёл проверки. Сохраняйте commit SHA и digest образа; тег latest сам по себе не является надёжным идентификатором релиза.

## Quality gates
- Не публиковать образ при провале обязательных тестов.
- Не давать недоверенному pull request доступ к production credentials.
- Не передавать credentials через логи или аргументы команд.
- Не разворачивать артефакт, отличный от проверенного.
- После deploy проверять реальный endpoint.

Локальный пример для образа, который слушает 8080 и имеет /health:

```bash
docker build -t demo-service:local .
docker run --rm -d --name demo-service -p 127.0.0.1:18080:8080 demo-service:local
curl --fail --show-error --max-time 3 http://127.0.0.1:18080/health
docker logs demo-service
docker stop demo-service
```

Подстройте порт и endpoint под контракт приложения. Привязка к 127.0.0.1 ограничивает доступ локальной машиной.

## Доверие и артефакты
Сохраняйте commit SHA, digest образа, результаты тестов, pipeline run, окружение и результат smoke test. Ограничивайте права runner и workflow. Изменение CI-конфигурации — изменение границы доверия: проверяйте сторонние actions, фиксируйте версии и не запускайте привилегированный deploy на непроверенном коде.

## Rollback
До выпуска определите предыдущую рабочую версию, критерии rollback и проверку после возврата. Откат приложения не отменяет автоматически миграции БД, внешние сообщения или изменения состояния.

## Практика
Внесите failing test и докажите, что publish/deploy не запускаются; исправьте тест, соберите образ и проверьте health endpoint. Зафиксируйте идентификатор образа.

## Контроль
1. Почему один commit должен проходить тесты и становиться источником релиза?
2. Чем тег отличается от digest?
3. Почему pull request не должен получать production credentials?
4. Что не откатывается возвратом образа?
5. Какие доказательства остаются после выпуска?

**Критерий освоения:** объясните цепочку commit → tests → image → smoke test → deploy → post-deploy verification и точки остановки при ошибках.
