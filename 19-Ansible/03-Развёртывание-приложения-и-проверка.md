# Ansible: безопасное развёртывание приложения и проверка результата

## Результат
Разделить подготовку хоста, выпуск версии и проверку приложения; делать изменение повторяемым и иметь понятный путь возврата.

## Предварительные знания
[Inventory и playbook](./01-Inventory-and-playbook.md), [Идемпотентность и check mode](./02-Idempotency-and-check-mode.md), Linux, SSH и права.

## 1. Разделите подготовку и выпуск
Роль подготовки сервера устанавливает системные зависимости, создаёт пользователя, каталоги и права. Шаг выпуска доставляет конкретную версию артефакта и меняет конфигурацию сервиса. Не смешивайте создание инфраструктуры, обновление приложения и миграцию данных в один непрозрачный playbook.

Пример структуры:
```text
playbooks/
  prepare.yml
  deploy.yml
roles/
  app_user/
  app_release/
```

## 2. Идемпотентность
Повторный запуск при неизменившихся входных данных не должен каждый раз менять систему. Предпочитайте Ansible-модули вместо shell-команд, где это возможно. Если используете command/shell, задайте условия изменения и проверьте, что повторный запуск не выдаёт ложный changed.

## 3. Версия и rollback
Передавайте идентификатор версии явно — например, commit или версию артефакта. Не скачивайте «последнюю версию» без фиксации конкретного результата. До deploy сохраните ссылку на предыдущую рабочую версию и определите, как проверить готовность после изменения.

Проверка должна измерять полезный результат: HTTP health endpoint, статус systemd-сервиса и логи. Успешный exit code Ansible сам по себе не доказывает доступность сервиса.

## 4. Практика
Используйте локальную виртуальную машину или контейнер с SSH в тестовой среде. Подготовьте отдельный playbook для пользователя и каталога, затем добавьте доставку демонстрационного сервиса. Выполните:
- `ansible-playbook --syntax-check`;
- `ansible-playbook --check --diff` с пониманием ограничений check mode;
- обычный запуск;
- повторный запуск и сравнение changed;
- проверку endpoint после выпуска.

Не выполняйте учебный playbook на production-хосте.

## Типичные ошибки
- Хранить пароль или приватный ключ в репозитории.
- Полагаться на check mode как на точную симуляцию любого модуля.
- Делать deploy по mutable tag без фиксации версии.
- Перезапускать сервис без проверки результата.
- Не иметь понятного пути возврата.

**Критерий:** повторный запуск playbook не вносит лишних изменений, версия однозначно определена, а результат выпуска подтверждён внешней проверкой.
