## 2. Быстрая проверка
Укажите точные команды для:
1. проверки пользовательского endpoint;
2. проверки health/readiness;
3. проверки процесса/контейнера;
4. чтения логов за интервал;
5. просмотра метрик и алертов;
6. определения текущей версии и digest образа.

Для каждой команды объясните ожидаемый результат и условие эскалации. Команда без интерпретации результата — неполный runbook.

## 3. Диагностическое дерево
```text
Запрос не работает
  -> DNS не разрешается? проверить резолвер и запись
  -> TCP не устанавливается? проверить маршрут, порт, listener
  -> TLS ошибка? проверить срок, SAN, цепочку и имя
  -> HTTP 5xx? проверить proxy, upstream и логи приложения
  -> процесс/контейнер падает? exit code, logs, ресурсы, конфигурация
  -> началось после релиза? сравнить версии, rollout и rollback-критерии
```
Это порядок локализации, а не универсальная гарантия: несколько слоёв могут отказать одновременно. Сохраняйте временные отметки и безопасные correlation ID.

## 4. Релиз и rollback
- Кто имеет право выпускать?
- Какие quality gates обязательны?
- Где найти commit, pipeline run и digest?
- Какая версия заведомо рабочая?
- Как проверить rollback?
- Есть ли миграции или изменения состояния, которые нельзя отменить автоматически?
- Кто принимает решение при частичном отказе?

Пошаговая инструкция должна быть проверена в тестовом окружении. Для разрушительных команд опишите предусловия, ожидаемый результат и восстановление.

## Критерий приёмки
Инженер, не участвовавший в создании сервиса, должен по документу найти владельца, локализовать пользовательский симптом, выполнить безопасную первичную диагностику, установить версию и понять, когда эскалировать. Проверяйте это практикой.
