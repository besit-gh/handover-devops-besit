## 1. Модель хранения

Полезно мыслить цепочкой:

`устройство → раздел → файловая система → точка монтирования → приложение`

- **Устройство** — например, `/dev/sdb`; оно может содержать несколько разделов.
- **Раздел** — например, `/dev/sdb1`.
- **Файловая система** — структура данных на устройстве: ext4, XFS и другие.
- **UUID** — идентификатор файловой системы, который часто используют в постоянной конфигурации.
- **Точка монтирования** — существующий каталог, через который становится доступно дерево файлов ФС.

Базовый осмотр:

```bash
lsblk -f
sudo blkid
findmnt
df -hT
```

Команды отвечают на разные вопросы. `lsblk -f` показывает дерево блочных устройств и точки монтирования; `blkid` помогает сверить UUID и тип; `findmnt` отражает фактические mount; `df` показывает использование ресурсов смонтированных файловых систем.

**Не делай вывод «диск пустой» только потому, что в каталоге нет файлов.** Сначала проверь, не смонтирована ли туда другая файловая система.

## 2. Ручное монтирование

Типичная последовательность для уже существующей файловой системы:

```bash
lsblk -f
sudo mkdir -p /srv/data
sudo mount /dev/sdb1 /srv/data
findmnt /srv/data
df -hT /srv/data
```

В реальной системе перед подключением нужно подтвердить устройство, тип и назначение. Не форматируй устройство, чтобы «заставить его заработать»: `mkfs` создаёт новую файловую систему и может уничтожить прежние данные.

Отключение:

```bash
findmnt /srv/data
sudo fuser -vm /srv/data   # если утилита установлена
sudo umount /srv/data
findmnt /srv/data
```

Если mount занят, выясни, какие процессы используют файлы. Не начинай с `umount -f` или ленивого `umount -l`: эти варианты не заменяют понимание последствий для приложения.

## 3. Постоянные подключения: /etc/fstab

Строка `fstab` обычно содержит шесть полей:

```text
<source> <mountpoint> <type> <options> <dump> <pass>
UUID=abcd-1234 /srv/data ext4 defaults,nofail 0 2
```

- `source` — устройство, UUID или другой допустимый источник;
- `mountpoint` — каталог назначения;
- `type` — тип файловой системы;
- `options` — параметры монтирования;
- `dump` — поле для старого механизма dump, часто `0`;
- `pass` — порядок проверки при загрузке для поддерживаемых ФС; детали зависят от системы.

Для постоянного подключения обычно предпочтительнее UUID, чем имя вроде `/dev/sdb1`, поскольку имена устройств могут меняться. UUID тоже нужно проверять: он может быть ошибочным или устаревшим.

### Безопасная проверка изменения

1. Сохрани копию текущей конфигурации.
2. Сверь UUID и тип ФС через `lsblk -f` и `blkid`.
3. Убедись, что точка монтирования существует.
4. Проверь конфигурацию командой `sudo findmnt --verify --verbose`, если версия util-linux поддерживает нужные проверки.
5. Выполни `sudo mount -a` и прочитай все ошибки.
6. Проверь фактическое состояние через `findmnt`, затем проверь файлы и приложение.
7. Только после проверки планируй перезагрузку. Для удалённого сервера заранее продумай доступ к консоли и откат.

`nofail` может быть уместен для необязательного диска, но **не исправляет** неверный UUID, неправильный тип ФС или отсутствие данных. Не добавляй этот параметр автоматически ко всем записям.

## 4. Диагностика нехватки места

### Блоки и inode — разные ресурсы

```bash
df -hT
df -i
du -xhd1 /var
```

- `df -hT`: использованные и доступные блоки, тип ФС.
- `df -i`: занятость inode. Огромное количество мелких файлов может исчерпать inode, даже если свободные блоки ещё есть.
- `du -xhd1 /var`: ориентировочный размер подкаталогов, не переходя на другие файловые системы; синтаксис зависит от реализации du.

Если `df` показывает заметно больше занятого места, чем удаётся найти через `du`, возможная причина — удалённый файл, который всё ещё открыт процессом. Если доступна утилита `lsof`, проверь:

```bash
sudo lsof +L1
```

Не удаляй журналы наугад и не перезапускай критичные процессы без оценки влияния. Сначала установи, какой процесс держит файл и можно ли безопасно ротировать журнал или перезапустить сервис.

## 5. Если каталог выглядит пустым после mount

Монтирование закрывает обзор на прежнее содержимое каталога назначения. Например, файлы, ранее лежавшие в `/srv/data`, временно скрыты под подключённой ФС; это не означает, что mount их удалил.

Проверка:

```bash
findmnt -no SOURCE,FSTYPE,OPTIONS /srv/data
ls -la /srv/data
```

Если это рабочий сервис, не отключай mount, пока не выяснишь, какие процессы используют каталог и что увидит приложение после отключения.

## 6. Ошибки ФС и состояние устройства

Для сообщений ядра можно использовать:

```bash
dmesg -T
journalctl -k
```

Ищи сообщения об I/O errors, ошибках драйвера, повреждении метаданных и переводе файловой системы в read-only. `fsck` нельзя бездумно запускать на смонтированной файловой системе: порядок действий зависит от типа ФС и состояния устройства. Для важных данных сначала оцени резервную копию или снимок, а затем выбирай подходящую процедуру восстановления.

## 7. Практический сценарий

**Симптом:** после перезапуска приложения каталог `/srv/data` выглядит пустым.

Собирай факты по порядку:

```bash
lsblk -f
findmnt /srv/data
grep -vE '^\s*(#|$)' /etc/fstab
sudo findmnt --verify --verbose
```

Дальше:

- если раздел не существует — исследуй обнаружение устройства и журналы ядра;
- если раздел существует, но не смонтирован — сверяй UUID, тип и запись `fstab`;
- если mount активен, но данных не видно — проверь источник, который действительно подключён к точке;
- после исправления проверь `findmnt`, ожидаемые файлы и работоспособность приложения.

Не начинай с `mkfs`, `fsck`, рекурсивного удаления или повторной перезагрузки без подтверждённой причины.

## Проверка готовности

Считай тему освоенной, если без подсказки можешь:

- показать, где в `lsblk -f` видны UUID, тип ФС и mountpoint;
- объяснить разницу между `df -h`, `df -i` и `du`;
- безопасно проверить изменение `fstab` до перезагрузки;
- объяснить, почему mount может скрыть старые файлы в каталоге;
- описать проверку результата после исправления инцидента.
