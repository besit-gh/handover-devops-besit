# Сквозной проект: контейнеризированный сервис с CI и восстановлением

## Цель
Собрать HTTP-сервис в Docker, проверить тестами, подключить CI, смоделировать неудачный релиз и передать систему другому инженеру с runbook.

## Архитектура
```text
Git commit -> validate -> tests -> build image -> smoke test
                                            |
                                  versioned image / digest
                                            |
                                      deploy -> verify
                                        |       |
                                        + failure -> rollback + notes
```
Сначала доведите локальный сценарий до воспроизводимости; registry и облако подключайте позже.

## Этап 1. Контракт сервиса
Документируйте endpoint, порт, health endpoint, переменные окружения, зависимости, запуск/остановку и ожидаемые логи. Health endpoint не должен раскрывать внутреннюю конфигурацию.

## Этап 2. Контейнеризация
Используйте [Dockerfile и build context](../16-Docker/03-Dockerfile-and-build-context.md). Ограничьте build context через .dockerignore, не копируйте credentials в образ, запускайте процесс без root, если возможно, и проверьте обработку SIGTERM. Убедитесь, что логи доступны через docker logs.

## Этап 3. Проверки
Добавьте тесты нормального ответа, некорректного ввода и health endpoint. Отдельно проверьте уже собранный образ: успешные unit tests не доказывают, что контейнер стартует. Следуйте [quality gates CI/CD](../18-CI-CD/03-Pipeline-quality-gates.md). Недоверенный pull request не должен получать права deploy.

## Этап 4. Выпуск
Свяжите каждый образ с commit и digest, сохраните результаты проверок. До выпуска определите предыдущую рабочую версию, критерии rollback и способ подтвердить восстановление. Откат приложения не отменяет автоматически миграции и внешние побочные эффекты.

## Этап 5. Наблюдаемость
Обеспечьте временные отметки в логах, health check, проверку endpoint и полезный сигнал ошибок/запросов. Не добавляйте user ID, request ID и полные URL как Prometheus labels. Свяжите практику с [Prometheus](../24-Prometheus/README.md), [Grafana](../25-Grafana/README.md) и [Production Operations](../34-Production-Operations/README.md).

## Этап 6. Инцидент
В локальном окружении разверните некорректную версию, например с неправильным портом health check. Соберите факты, проверьте гипотезу, исправьте причину или выполните rollback. Сценарий: [Неудачный релиз контейнерного сервиса](../91-Labs-Incidents/02-Container-release-failure.md). Не используйте production для учебных отказов.

## Этап 7. Handover
Заполните [Runbook и эскалацию](../92-Handover-Book/02-Runbook-and-escalation.md): владелец, архитектура, команды проверки, логи, метрики, выпуск/откат, зависимости и риски. Не включайте credentials.

## Критерии приёмки
- [ ] Сервис собирается из чистого checkout.
- [ ] Тест ловит намеренно внесённую ошибку.
- [ ] Провал quality gate блокирует публикацию.
- [ ] Образ проходит smoke test и связан с commit.
- [ ] Неудачный релиз диагностирован по фактам и восстановлен.
- [ ] Runbook позволяет другому инженеру проверить сервис и выполнить rollback.
- [ ] В репозитории и логах нет credentials.
- [ ] Документация описывает открытые риски.

## Защита проекта
Объясните, чем тест отличается от smoke test, как связать контейнер с commit, как отличить отказ приложения от ошибки прокси и почему rollback может не отменить изменение данных.
