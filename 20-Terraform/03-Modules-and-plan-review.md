# Terraform: модули и проверка плана

## Результат обучения

Вы научитесь выделять повторно используемую конфигурацию в модуль и проверять план изменений на неожиданное создание, замену или удаление ресурсов.

## Предварительные знания

- [Plan и apply](./01-Plan-and-apply.md)
- [State и drift](./02-State-and-drift.md)
- Git: ветки и code review.

## 1. Когда нужен модуль

Модуль — это набор Terraform-конфигурации, который можно вызвать из корневого проекта. Модуль полезен, когда повторяется осмысленная единица инфраструктуры с понятными входами и выходами, а не просто ради сокращения числа строк.

Пример структуры:

```text
infra/
├── main.tf
├── variables.tf
├── outputs.tf
└── modules/
    └── storage/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
```

В корневом модуле вызов выглядит примерно так:

```hcl
module "storage" {
  source      = "./modules/storage"
  bucket_name = var.bucket_name
}
```

Имя ресурса и аргументы внутри дочернего модуля не становятся автоматически доступны вызывающему коду. Значения, нужные снаружи, следует публиковать через `output`. Не помещайте реальные ключи доступа в variables или tfvars, которые могут попасть в Git.

## 2. Интерфейс модуля

Хороший интерфейс задаёт необходимые входы, разумные defaults и outputs с полезными значениями. Не создавайте универсальный модуль с десятками флагов, если он скрывает поведение и затрудняет review.

Проверяйте:
- обязательные и необязательные inputs;
- ограничения допустимых значений;
- версии Terraform и provider;
- документированные outputs;
- naming/tagging conventions;
- безопасные defaults и права доступа.

## 3. Plan — не формальность

Базовый рабочий цикл:

```bash
terraform fmt -check -recursive
terraform validate
terraform plan -out=tfplan
terraform show tfplan
```

План может содержать чувствительные значения. Не публикуйте его в общедоступных артефактах и ограничьте доступ к CI-логам. Файл plan — не обычный текстовый отчёт, а сохранённый план для последующего применения.

Перед apply просмотрите:
1. Какие ресурсы будут созданы?
2. Какие атрибуты изменятся на месте?
3. Какие ресурсы будут заменены?
4. Что будет уничтожено?
5. Почему это изменение необходимо?
6. Каковы blast radius, rollback/restore path и ожидаемое влияние?

Знак `-/+` в плане обычно указывает на замену ресурса: старый объект будет уничтожен, а новый создан, хотя конкретный порядок зависит от типа ресурса и настроек. Замена диска, базы или сетевого адреса может иметь серьёзные последствия.

## 4. Практика без облачных затрат

Создайте учебный модуль, который принимает строковую переменную и выдаёт нормализованное значение через output, либо используйте локальный provider в изолированной лаборатории. Выполните fmt, validate и plan. Измените входное значение и сравните планы.

Не применяйте изменения к рабочему аккаунту только ради упражнения. Если используете облако, задайте бюджет, отдельный учебный проект и очистите созданные ресурсы после проверки.

## 5. Ошибки при работе с модулями

- Дублировать модуль без общего интерфейса и затем исправлять копии по-разному.
- Изменить source или версию provider без review влияния.
- Считать, что модуль сам по себе делает инфраструктуру безопасной.
- Применить plan, который не соответствует текущему коду или состоянию.
- Игнорировать замены ресурсов и потенциальное удаление данных.

## Контроль понимания

1. Когда модуль полезнее копирования конфигурации?
2. Чем outputs отличаются от локальных значений дочернего модуля?
3. Почему нужно проверять замену ресурса отдельно от изменения на месте?
4. Какие данные в plan могут потребовать ограниченного доступа?
5. Какие проверки следует выполнить до apply?

**Критерий освоения:** подготовьте небольшой модуль, покажите его интерфейс и объясните каждое разрушительное или заменяющее действие в плане.
