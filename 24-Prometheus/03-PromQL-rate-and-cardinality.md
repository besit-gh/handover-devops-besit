# Prometheus: PromQL, rate и cardinality

## Результат обучения

Вы сможете отличать counter от gauge, выбирать базовый способ расчёта скорости событий и избегать label-значений, которые взрывают число временных рядов.

## Предварительные знания

- [Метрики и targets в Prometheus](./01-Metrics-and-targets.md)
- [Alerting rules](./02-Alerting-rules.md)

## 1. Тип метрики задаёт смысл запроса

- **Counter** — монотонно растущая величина, которая может сбрасываться при перезапуске процесса: например, общее число HTTP-запросов.
- **Gauge** — значение, которое растёт и падает: например, число активных соединений или текущая температура.

Для counter обычно важна скорость роста, а не только накопленное значение. Например:

```promql
rate(http_requests_total[5m])
```

Это оценивает среднюю скорость изменения counter в секунду на пятиминутном окне и учитывает обнаруживаемые сбросы. Для общего прироста за окно используйте:

```promql
increase(http_requests_total[1h])
```

Окно влияет на компромисс между отзывчивостью и шумом. Маленькое окно быстрее реагирует, но может быть нестабильным при редком scrape; большое сглаживает, но задерживает видимые изменения.

## 2. Сохраняйте нужную размерность

Чтобы посмотреть скорость по HTTP-коду:

```promql
sum by (status) (rate(http_requests_total[5m]))
```

Чтобы получить общую скорость по всем кодам и экземплярам:

```promql
sum(rate(http_requests_total[5m]))
```

Если отбросить все labels суммой, можно потерять важную для расследования детализацию. Если сохранить слишком много labels, запрос и хранение станут дорогими. Выбирайте группировку под вопрос, на который отвечает график или alert.

## 3. Cardinality: labels не должны быть бесконечными

Каждая уникальная комбинация имени метрики и значений labels создаёт отдельный time series. Хорошие кандидаты: ограниченные значения вроде HTTP method или status class. Опасные кандидаты: user ID, email, произвольный URL с идентификатором, request ID или полный текст ошибки.

Если в метрику добавляется label `user_id`, число рядов может вырасти почти пропорционально числу пользователей, а комбинации нескольких labels перемножают количество вариантов. Для подробных событий используйте логи или traces, а не превращайте каждое событие в отдельный ряд метрик.

## 4. Практическая лаборатория

В интерфейсе Prometheus или тестовом наборе метрик выполните:

```promql
rate(http_requests_total[5m])
sum by (job) (rate(http_requests_total[5m]))
sum by (status) (rate(http_requests_total[5m]))
increase(http_requests_total[1h])
```

Сравните ответы и объясните, какие labels остаются в каждом результате. Затем сформулируйте, почему график по `request_id` — плохая идея.

Для диагностики пустого результата проверьте, существует ли имя метрики, есть ли нужные labels, доступны ли samples в выбранном диапазоне и скрейпится ли target. Не делайте вывод, что значение равно нулю, если на самом деле ряд отсутствует.

## 5. Частые ошибки

- Применять `rate()` к gauge.
- Считать counter без rate/increase и не замечать изменения частоты событий.
- Использовать слишком короткое окно при редком scrape.
- Терять нужную размерность через слишком ранний `sum`.
- Добавлять высококардинальные labels и резко увеличивать объём TSDB.
